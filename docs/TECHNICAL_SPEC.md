# TowerDefence — техническое задание

**Версия:** 1.0 · **Платформа:** браузер (desktop/mobile) · **Стек:** HTML5, CSS, нативный JavaScript ES Modules, Canvas 2D без игровых движков и UI-фреймворков.

Документ применяется вместе с [GAME_DESIGN.md](GAME_DESIGN.md) и [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md). Все цифры баланса настраиваются данными, а не хардкодом. Неопределённые решения следует реализовать максимально просто с сохранением расширяемости.

## 1. Обязательные архитектурные принципы

1. Игровая логика отделена от рендеринга и DOM. Тесты симуляции запускаются без Canvas.
2. Реальный размер экрана и соотношение сторон не влияют на характеристики объектов, пути врагов и скорость игрового времени.
3. Вся конфигурация миссий, волн, противников, башен, технологий и наград описана в версионируемых JS/JSON данных со схемой валидации.
4. Модули общаются через явные функции и события; не используют неограниченный доступ к глобальным переменным.
5. Одна игровая сессия имеет единственный источник истины для состояния симуляции; UI не изменяет HP/ресурсы напрямую.
6. Для воспроизводимости и тестирования рандом (если будет введён) должен получать контролируемый seed.
7. Проект стартует в браузере как статические файлы через простой локальный HTTP-сервер; сборщик/транспайлер не требуется для работы игры.
8. Допускаются инструменты разработки и тестов через npm (например, Vite как dev server, Vitest или Playwright), но **в runtime не используются React/Vue/Phaser/Pixi/Three и аналогичные библиотеки**.

## 3. Состояния приложения

Верхнеуровневые экраны: `mainMenu`, `camp`, `planetMap`, `briefing`, `mission`, `results`, `settings`. Переходы разрешаются централизованным роутером/автоматом состояний.

Состояния миссии: `loading → preparation → combat ↔ intermission → victory|defeat → results`. Дополнительное `paused` — флаг поверх combat/intermission, а не второе состояние, которое может конфликтовать с терминальным исходом.

- При выходе с незавершённой миссии прогресс попытки не сохраняется, пользователь подтверждает уход.
- Настройки и постоянный прогресс сохраняются; состояние в бою — временное.
- После victory/defeat любые повторные callbacks от animation frame игнорируются.
- Повторный запуск миссии создаёт **новый** объект состояния, не переиспользуя массивы врагов/таймеры старой.
- Навигация браузера назад из миссии не приводит к потере прогресса без подтверждения; на остальных экранах может использовать History API.

## 4. Игровой цикл и расчёт времени

Использовать `requestAnimationFrame` для визуализации и **фиксированный шаг симуляции 1/60 с** с аккумулятором. При каждом кадре:

```js
const STEP = 1 / 60;
const MAX_FRAME_DELTA = 0.25;
const MAX_STEPS = 8;

function frame(nowMs) {
  const elapsed = Math.min((nowMs - previousMs) / 1000, MAX_FRAME_DELTA);
  previousMs = nowMs;

  if (!paused && missionIsRunning()) {
    accumulator += elapsed * speed; // speed = 1 или 2
    let steps = 0;
    while (accumulator >= STEP && steps < MAX_STEPS) {
      updateSimulation(STEP);
      accumulator -= STEP;
      steps++;
    }
    if (steps === MAX_STEPS) accumulator = 0; // не допускаем бесконечного догоняния
  }

  render(snapshot(), accumulator / STEP);
  requestAnimationFrame(frame);
}
```

Этот код иллюстрирует принцип; при внедрении учитывать первый frame без previousMs. Таймеры миссии, движение, кулдауны, DoT и спавны считают **игровые секунды**, не `Date.now()`. 2× увеличивает игровое время пропорционально; при падении FPS допустимо временное замедление относительно реального времени, но не скачкообразное перемещение врагов через критические цели. После возвращения из фоновой вкладки не делать «догоняющие» минуты симуляции: автоматически ставить паузу.

Изменения состояния применяются в последовательности: ввод команд → перемещение/спавн → наведение/выстрел → попадания/статусы → нанесение урона целям → смерть/награды → цели/завершение. Терминальный исход фиксируется один раз.

## 5. Координаты, карта и камера

- **Мировые координаты:** непрерывные единицы; 1 клетка = 64 мировых единицы.
- **Логические координаты клетки:** `{col,row}`; не зависят от DPR.
- **Экранные координаты:** CSS-пиксели в области canvas после вычета его bounding box и transform камеры.
- **Указатель:** pointer events для mouse/touch/pen, `touch-action: none` только у canvas; прокрутка внешних элементов сохраняется.
- **Камера:** `{x,y,zoom}`, transform мир→экран и обратный, нормализация положения при resize/rotation, ограничение видимой области границами карты там, где это возможно.
- **Retina:** canvas.width = CSS width × `devicePixelRatio`, canvas.height аналогично, затем `ctx.setTransform(...)`; максимальный внутренний DPR можно ограничить 2 ради производительности.
- **ResizeObserver:** перестраивает canvas и слои, не меняя игровое время и состояние объектов.
- **Узкие экраны:** камера может показывать меньшую часть мира, HUD не должен перекрывать обязательные точки подтверждения.
- **Не предугадывать aspect ratio:** отдельные landscape/portrait перестановки UI по CSS media/container queries, без смены логики игры.

### 5.1. Карта

Конфиг содержит размеры, непроходимые клетки, `buildCells`, `trapCells`, `spawnPoints`, `groundTargets`, `waypoints`, `objectives`. Предусмотреть несколько входов, несколько целей, движущуюся точку и воздушный коридор.

Наземная навигация: A* или BFS на клеточной маске с учётом движения по четырём направлениям; диагонали не используются в MVP во избежание «срезания углов». Для каждой установки башни проверять достижимость всех актуальных маршрутов врагов. Если размещение изменило проходимость, обновлять маршруты **до** списания денег. Повторные расчёты кэшируются в отсутствие изменений карты. На больших картах предпочтительны flow fields для группы врагов с общей целью, но это оптимизация, не требование MVP.

Воздушные враги используют waypoint-маршрут с заданной скоростью и не требуют наземного pathfinding.

## 7. Подсистемы симуляции

### 7.1. Волны

Волна создаёт спавны по игровому времени; все спавны имеют IDs и расписание. Если лимит активных врагов достигнут, следующая группа ожидает свободного места, а не пропускается. Счётчик `spawnedCount` и статус завершения гарантируют, что никого не создают дважды после паузы.

### 7.2. Цели и научные сценарии

Общий интерфейс `objective.update(dt, state)`, `objective.getProgress()`, `objective.isComplete()`, `objective.getFailureReason()`, `objective.getHudText()`. Реализации: установка по таймеру, удержание безопасной зоны, доставка и монтаж, сопровождение по waypoint.

У миссии может быть несколько обязательных проверок, объединяемых AND. Провал — OR. Параметры условий задаются в данных и доступны UI.

### 7.3. Бой

Поиск целей — только валидные враги по типу и дальности; сортировка детерминирована (при равенстве по ID). Выстрел и попадание — отдельные события, чтобы позже добавить летящие снаряды. В MVP разрешены мгновенные попадания, кроме гаубицы с коротким визуальным временем полёта (урон в момент попадания по актуальному положению цели). Эффекты замедления и сопротивлений централизованы. Каждая смерть сообщает `enemyKilled` один раз.

### 7.4. Строительство

Перед покупкой проверять фазу миссии, доступность по технологии, тип клетки, пересечение, достижимость, наличие ЭС, лимит юнитов. Выполнять валидированную транзакцию: списание → создание объекта → событие → обновление HUD. При ошибке ничего не списывать.

### 7.5. Мобильные юниты

Нативные команды `selectUnit(id)` и `moveUnit(id, worldPosition)`. Наземные юниты следуют навигационной сетке, дроны летают по прямой в пределах карты. Перемещение не прерывает рендеринг и может быть отменено новой командой. Состояние destroyed терминально для конкретного экземпляра.

## 8. Модель метапрогресса и сохранения

Хранение: `localStorage` для MVP с JSON и версией схемы; не сохранять циклические ссылки, HTML-объекты или классовые инстансы.

```json
{
  "schemaVersion": 1,
  "campaignId": "nova7-main",
  "unlockedSectorIds": ["sector-01"],
  "sectors": {
    "sector-01": {
      "briefingSeen": false,
      "firstVictoryClaimed": false,
      "bestStars": 0,
      "victories": 0,
      "attempts": 0
    }
  },
  "resources": { "materials": 0, "data": 0 },
  "research": {},
  "settings": {
    "musicVolume": 0.7,
    "sfxVolume": 0.8,
    "reducedMotion": false,
    "quality": "auto"
  }
}
```

- Схема мигрируется функцией `migrateSave(old)`; отсутствующие поля заменяются валидными значениями, неизвестные IDs игнорируются с диагностикой.
- Записи атомарно формируются как новый JSON объект после валидации. Ошибка квоты/доступа localStorage показывается пользователю и не останавливает игру; в текущей сессии данные остаются в памяти с предупреждением, что не сохранятся.
- Награда выдаётся один раз в обработчике первой победы, `firstVictoryClaimed` меняется в **том же** изменении состояния, что и начисление валюты.
- Повторный переход на экран результатов не вызывает обработчик награды.
- `attempts` увеличивается при старте боя, не при просмотре брифинга.
- `victories` увеличивается при успешном завершении попытки.
- Лучшие звёзды не уменьшаются при повторной неудаче.
- Кнопка «Новая игра» с явным подтверждением; невозможно случайно стереть прогресс.
- Не обещать кросс-девайс синхронизацию без сервера. При очистке хранилища браузера сохранения могут быть потеряны. Экспорт/импорт сохранения в JSON — **желательное дополнение после MVP**.

## 9. DOM, Canvas и обработка ввода

Canvas рисует карту, юнитов, эффекты, траектории и маркеры мира. HTML/CSS рисует HUD, диалоги, брифинг, кнопки и формы: обеспечивается доступность, перенос строк, системный масштаб текста.

- Все сенсорные события обрабатывать через Pointer Events с pointer capture для перетаскивания камеры; отличать tap от pan порогом движения (ориентир 8 CSS px).
- Клик по полю в режиме строительства создаёт **предпросмотр**, не списывает ЭС; явное подтверждение покупки.
- Подсветить недопустимую клетку и объяснить причину в текстовом уведомлении.
- Отдельные режимы: `inspect`, `placeTower`, `placeTrap`, `selectUnit`, `moveUnit`, `pan`.
- Жест масштабирования двумя пальцами либо две доступные экранные кнопки ±; увеличение фиксируется вокруг точки жеста/центра видимой области.
- На ПК поддержать Escape/Space/WASD и видимый keyboard focus; предотвратить прокрутку страницы пробелом **только** при активной игре и отсутствии ввода в форме.
- Resize, изменённый DPR, hidden/visible и orientation change не изменяют состояния миссии.

## 10. Минимальные требования к производительности

Целевые эксплуатационные показатели для MVP (проверяются на реальных устройствах и корректируются после профилирования):

| Метрика | Цель |
|---|---|
| Desktop среднего класса | ~60 FPS при ≤ 60 врагах |
| Типичный мобильный браузер последних лет | ≥ 30 FPS при ≤ 60 врагах |
| Логика симуляции | 60 фиксированных шагов/игровую секунду, без frame-dependent урона |
| Первый интерактивный экран | Ориентир до 3 с на типичном мобильном интернете после кэширования; измерять отдельно холодный запуск |
| Размер исходных контентных файлов | Предпочтительно ≤ 10 МБ для MVP без тяжёлых аудио/видео |
| Время восстановления после смены ориентации | Без сброса миссии, экран корректен со следующими кадрами |

Меры: отрисовывать только видимую область; предварительная загрузка спрайтов; переиспользование массивов временных эффектов по необходимости; избегать reflow на каждом кадре; ограничение DPR; отключаемые частицы; кеширование путей и сортировок там, где это даёт выигрыш. Разрешить `prefers-reduced-motion`.

Метрики не гарантированы абстрактным браузером и измеряются на целевых тестовых устройствах.

## 11. Ошибки, диагностика, безопасность

- Проверять данные перед запуском; при ошибке конфигурации показывать понятный экран «Не удалось загрузить миссию», логировать подробности разработчику.
- Ассеты: при недоступности изображения подставлять геометрический placeholder, при отказе аудио играть без звука.
- Не подставлять пользовательский текст через `innerHTML`; для динамического текста использовать `textContent`.
- Не использовать `eval` или выполнение кода из сохранений.
- В MVP нет сторонних API и отправки пользовательских данных.
- `window.onerror`/ `unhandledrejection` для отладки не должны приводить к зацикленному показу диалогов.
- Можно добавить debug overlay для разработчика (FPS, враги, seed, состояние волны, paths), отключённый в обычном интерфейсе.

## 12. Тестовая стратегия

**Unit:**
- Расчёт урона/бронепробития, складывание замедлений, кулдауны, цели и приоритеты.
- Стоимость покупки/улучшения/продажи, отсутствие отрицательной ЭС.
- A*/BFS и запрет полной блокировки пути.
- Волны создают точное количество врагов; награда за убийство не дублируется.
- Проверка дополнительных звёзд и приоритета проигрыша.
- Состояние кампании: доступность новых секторов, первая премия ровно один раз.

**Integration:**
- `briefing → preparation → combat → results → camp`.
- Детерминированное воспроизведение миссии при одном сценарии команд.
- Пауза и 2× не меняют игровой исход при одинаковой последовательности игровых шагов.
- Сохранение, перезагрузка страницы, миграция старой версии, повреждённый JSON.
- Разворот экрана во время боя, изменение размера и восстановление после фоновой вкладки.
- Миссия 06: сопровождение, гибель группы, завершение эвакуации.

**E2E (реальные браузеры):**
- Desktop Chromium/Firefox/WebKit (в рамках доступной среды тестов).
- Mobile viewport 360×800, 390×844, 800×360, tablet 768×1024, wide 1920×1080; плюс необычные размеры, например 523×523.
- Установка башни касанием с подтверждением, масштабирование, панорамирование, пауза, диалоги, архив, брифинг.
- Основная игра без горизонтального overflow на страницах UI; камера может перемещаться внутри canvas.
- Keyboard-only навигация главного меню/карты/брифинга/результатов.
- Автоматическая проверка 6 MVP конфигов на достижимость, валидные ссылки и выполнимость миссий в тестовом сценарии.

## 13. Критерии технической приёмки

- Приложение работает без игровых движков и runtime-фреймворков на чистом JS.
- Проект можно запустить по README; статический build не требует сервера с игровой логикой.
- Данные миссий загружаются из конфигов; добавление новой миссии не требует правки боевой логики.
- Перерисовка и resize не изменяют симуляцию.
- Ни один критический сценарий не требует hover или исключительно мыши.
- Нет блокирования обязательных маршрутов строительством и нет двойного начисления ресурсов.
- Сохранение переживает reload и переход между экранами; испорченная запись обрабатывается без падения приложения.
- Автотесты покрывают критическую экономику, прогрессию, навигацию и результаты.
- Документация и фактические механики не противоречат друг другу; балансные изменения отражаются в таблицах конфигов.
